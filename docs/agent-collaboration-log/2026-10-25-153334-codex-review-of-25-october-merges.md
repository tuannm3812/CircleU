### F1 — Medium: unconfigured Firebase silently accepts circle operations as local successes

- **Location:** `Circleu/Stores/CircleStore.swift:53`, `:136`, `:196`, `:272`, `:550`, `:558` ([source](../../Circleu/Stores/CircleStore.swift)); introduced by PR #3's optional service and optional calls.
- **Evidence:** With a missing/mismatched Firebase configuration, the service is permanently nil for that store. `createCircle` and `addPost` still insert and save locally before calling the optional remote operation. Join and delete likewise mutate locally without reporting that the remote operation did not happen. The existing UI closes the creation form at `Circleu/Features/Circle/CircleView.swift:244` and clears the shared-post draft at `Circleu/Features/Circle/CircleSheets.swift:201`; neither receives an unavailable-backend result.
- **Reachable condition:** This is not limited to unsigned test fixtures. `FirebaseRuntime.makeAuthenticator()` selects `NoOpFirebaseAuthenticator` when unconfigured. That existing adapter returns a session from `signIn` (`Circleu/Services/FirebaseAuthService.swift:102`), and `BackendSessionStore.wireBackendStores` passes its UID to CircleStore (`Circleu/Stores/BackendSessionStore.swift:59`). Consequently, an unconfigured app can appear signed in and present social actions while all the newly optional circle writes do nothing. A cached circle/post deletion also cannot remove the server copy. This is a source-traced consequence, not a reproduced device/backend incident.
- **Impact and attribution:** Preventing the launch crash is correct. The gap is exposing the formerly crashing configuration as an apparently working social flow without a visible local/unavailable state. No-op authentication and suppressed remote errors predate these merges; this finding does not attribute their implementation to PR #3. The guard is not implementation or verification of the approved local-first migration.
- **Proposed fix:** Retain safe startup, but make backend availability explicit at the store/UI boundary. Disable remote circle actions with an explanation when unavailable, or explicitly identify a separate local demo mode; preserve a draft when sharing cannot occur. Do not claim a remote deletion succeeded after only removing a local cache item. Restrict successful fake authentication to explicitly injected test/preview dependencies. Add focused missing-configuration coverage for attempted create/share/delete and configured-service coverage in an isolated test environment before a follow-up PR is accepted.

### F2 — Low: simulator discovery succeeds with no selected iPhone

- **Location:** `.github/workflows/ci.yml:33–43` ([workflow](../../.github/workflows/ci.yml)).
- **Evidence:** Executed the exact embedded Python selector in memory against synthetic `simctl` JSON. Both an empty device map and an iPad-only map returned exit 0 and empty stdout. The next `grep "$SIM_ID"` is then `grep ""`, which also returned 0 with a nonempty listing. Thus discovery appears successful, publishes an empty `SIM_ID`, and passes `platform=iOS Simulator,id=` to xcodebuild. No false green test run is claimed: the later test invocation still lacks a usable destination.
- **Impact:** On a runner with no available iPhone, failure is deferred to an unrelated-looking xcodebuild destination error instead of clearly identifying missing runner prerequisites.
- **Proposed fix:** Make the selector exit nonzero with a useful error when no phone is found, and validate nonempty `SIM_ID` before writing to `GITHUB_ENV`. Prefer explicit runtime identifier validation over accepting every key containing `iOS`. A synthetic nonnumeric runtime suffix currently raises `ValueError`; that is a robustness observation, not evidence that GitHub currently emits that format. Add an explicit nonempty/valid developer-directory check to Xcode selection for similarly clear diagnostics.
